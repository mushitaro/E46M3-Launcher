# TUNER 側 実装指示書 — 再起動後の復帰

**日付**: 2026-08-09
**相手**: `E46M3CSL_TuningTool`（`mss54hp-csl-convert-tuner.tsunagi.app`）
**ランチャー側**: 実装済み・ビルド通過（`app.tsunagi.e46m3.launcher`）

証拠ラベル: **[V]** 実機で確認　**[I]** 推論　**[U]** 未確認

---

## 1. 直したい体験

データログを終えてキーをオフ → オンに戻すと、**ヘッドユニットが必ずコールドブートする** **[V]**。Chrome ごと落ちるので TUNER は真っさらな初期画面で立ち上がる。

**データは失われていない。** IndexedDB は再起動を越える。失われるのは**居場所**だけ — どのセッションを見ていたか。今そこへ戻る道は復旧（バックアップ）導線であり、それは「あるべき保険」であって「毎回通る道」ではない。

---

## 2. 分担

| | できるのは |
|---|---|
| **再起動後に TUNER を前面に戻す** | **ランチャーだけ。** 死んだ Web アプリは自分を起動できない |
| **どのセッションを開くか** | **TUNER だけ。** IndexedDB を持っているのはそちら |

ランチャーが運べるのは**「これは復帰である」という事実ひとつ**だけ。中身の判断はしない（できない）。

---

## 3. ランチャーが渡すもの — これが唯一の契約

復帰起動のときだけ、URL に **`?resume=1`** が付く。

```
通常の起動   https://mss54hp-csl-convert-tuner.tsunagi.app/
復帰の起動   https://mss54hp-csl-convert-tuner.tsunagi.app/?resume=1
```

それだけ。他のパラメータもヘッダも `postMessage` も無い。

### ランチャー側の挙動（そちらが前提にしてよいこと）

- **`?resume=1` が付くのは、前回 TUNER が前面のまま電源が落ちた場合のみ** **[V]**
- **1回きり。** 復帰記録は起動を試みる前に消える。TUNER が起動時に落ちても、次のキーサイクルは素のコンソールに戻る
- **オーナーが3秒以内に画面へ触れたらキャンセルされ、`?resume=1` の起動自体が起きない**
- コンソールに戻ってきた時点で記録は消える。「M → TUNER と自分で押した」あとに電源が落ちれば、また付く

## 4. TUNER 側にお願いしたいこと

### 4.1 必須 — `?resume=1` で直近セッションを開く

```
起動時に URLSearchParams が resume=1 を持つ
  → 直近の（＝中断された）ログセッションを開いた状態で立ち上げる
  → 復旧/バックアップ導線を経由させない
```

**「復元しますか？」を出さないでほしい。** 復帰であることは既にランチャー側が判定し、オーナーは3秒間それを見て止めなかった。ここで再度確認を挟むと、確認が2回になるだけで体験は改善しない。

### 4.2 必須 — `resume=1` が無いときの挙動は変えない

通常起動の見え方は今のままで構わない。**この指示書は復帰経路だけの話**であり、初期画面の設計変更を求めていない。

### 4.3 復帰できるものが無かった場合

中断セッションが存在しない（初回、あるいは正常に閉じた後）なら、**黙って通常起動でよい**。エラーもトーストも不要。ランチャーは「前面だった」ことしか知らず、「未完了の作業があった」ことは知らないので、**空振りは正常系**である。

### 4.4 URL の後始末（任意）

`?resume=1` を読んだあと `history.replaceState` でクエリを落としておくと、そのあとリロードされた時に二重に復帰扱いにならない。**Service Worker には影響しない** — ナビゲーションは `request.mode === 'navigate'` で `/index.html` に解決されるので、クエリの有無でキャッシュは外れない **[V]**。

---

## 5. 触ってはいけないもの

### 5.1 Service Worker のナビゲーション処理

`?resume=1` はクエリなのでキャッシュキーには影響しないが、**ナビゲーションを `caches.match(request)` に変えないこと**。今は `/index.html` 固定で引いており、これがクエリ付き URL でもオフラインで動く理由。リクエストそのもので引くと `?resume=1` はキャッシュに無いので、**オフライン時の復帰が必ず失敗する**。

### 5.2 `/` を precache に足さないこと

`useAppUpdate` の更新検出が `/` を要求してキャッシュを外し、ネットワークに出ることで成立している。precache に `/` を入れると**更新検出が永久に死ぬ**。既に `useAppUpdate.ts` に書かれているが、ここにも書いておく。

## 6. 動作確認

車両が要る。ランチャー側は導入済みなので、TUNER 側を出したあと:

```bash
bash tools/deploy.sh          # サイト疎通 → 導入 → TUNER を1回開いてキャッシュ更新
```

そのうえで実車で:

1. TUNER を開く（M → TUNER）
2. データログを1本取る
3. **キーオフ → キーオン**
4. コンソールが出て、LCD の通知行に `TUNER IN 3 / 2 / 1`
5. 触らなければ TUNER が全画面で開き、**さっきのセッションが出ている**
6. もう一度キーサイクルし、今度は**カウント中に画面へ触れる** → コンソールのまま

## 7. 未確認 [U]

- 復帰起動時に Chrome のセッションが温まりきらず Custom Tab（ツールバー付き）で開く可能性。3秒の待ちはこれも兼ねているが、コールドブート直後の負荷（load average 30超 **[V]**）で足りるかは未確認
